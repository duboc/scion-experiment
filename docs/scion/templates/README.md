# Agent templates

One folder per role, plus `_shared/agents.md`: the operating protocol every agent follows. Values such as
`${SANDBOX_PROJECT}` are placeholders; render them with your `config/factory.env`:

```bash
scripts/render-templates.py            # -> build/templates/<role>/ (git-ignored)
```

## The team

| Role | Project | Harness | GCP identity | Purpose |
|---|---|---|---|---|
| `lead` | build | Claude Code | Hub VM SA (passthrough) | plans and delegates issues, reviews diffs, hands over to the PO; never codes |
| `backend` | build | OpenCode (Gemini 2.5 Pro) | Hub VM SA | Go service and SQL |
| `frontend` | build | Antigravity | Hub VM SA | UI |
| `reviewer` | build | Hermes (Gemini 2.5 Pro) | Hub VM SA | tests and ADR verdicts |
| `deployer` | build | Claude Code | `${DEPLOYER_SA}` (assign) | migrations, Cloud Run deploys, live checks, rollback |
| `eval-lead` | eval | Antigravity | Hub VM SA | measures the build factory; orchestrates the eval team |
| `factory-analyst` | eval | Antigravity | Hub VM SA | agent activity and issue-flow analysis |
| `search-evaluator` | eval | Antigravity | Hub VM SA | live relevance and latency probes, `eval_runs` |
| `ui-craftsman` | eval | Antigravity | Hub VM SA | dashboard design (Impeccable skill) |
| `eval-deployer` | eval | Antigravity | `${DEPLOYER_SA}` (assign) | dashboard deploys |

Mixing harnesses was deliberate (to compare them) and has a cost: each one failed differently (L3 OpenCode model
catalog, L4 Hermes printing instead of messaging, L6 Antigravity hooks). In this run the Claude Code agents (lead,
deployer) had the fewest harness-specific problems.

## Files in a role folder

| File | Scion field | Notes |
|---|---|---|
| `scion-agent.yaml` | the template config | `default_harness_config`, `system_prompt`, `agent_instructions`, `env` (`FACTORY_ROLE` and, for deployers, the sandbox project), `telemetry` |
| `system-prompt.md` | `system_prompt` | what is specific to the role |
| `agents.md` | `agent_instructions` | generated by `render-templates.py` from `_shared/agents.md` (+ the role's `agents.extra.md`, if any) |
| `home/...` | home overlay | copied into the agent's home. The OpenCode and Hermes harness-configs run `sh /home/scion/.local/bin/<harness>-launch.sh`, so the launchers live here. |

Harnesses that don't support a native system prompt (OpenCode, Hermes) get the system prompt prepended to the
instructions file; you don't have to do anything about it.

The GCP identity is not part of the template: assign `${DEPLOYER_SA}` to the deployer agents in the Hub (see
[setup-runbook.md](../setup-runbook.md), step 6).

## Uploading to the Hub

Use the Scion CLI, from a machine logged in to the Hub, inside a checkout linked to the Hub project:

```bash
cp -R build/templates/lead .scion/templates/lead
scion templates push lead          # project scope; add the root --global flag for a global template
scion templates show lead          # check the files and the harness
```

Each template must have its own files. The original factory seeded its templates by writing rows straight into the Hub
database, and five eval templates ended up pointing at the `frontend` template's files (L16). Don't edit the Hub DB.

> [!NOTE]
> The push flow above is the supported CLI path, but it was not exercised end to end on this factory's Hub (the
> templates there were created before these docs). Check the result with `scion templates show` before you start
> agents from it.

Template changes apply when an agent starts. Running agents keep their old prompt until they are restarted or
reincarnated (see [operations-runbook.md](../operations-runbook.md)); in the meantime, send the rule change as a
message.

## What changed compared with the templates the factory first ran with

- One shared protocol (`_shared/agents.md`) instead of rules copied into every prompt, and `agents.md` no longer
  duplicates the system prompt.
- The old rule "Do NOT run `sciontool status`" is reversed: every agent ends every turn with `sciontool status
  blocked | task_completed | ask_user`, so the Hub stops flagging idle agents as STALLED (L5).
- Agents must see `Message delivered` after `scion message`; printed text reaches no one (L4).
- Evidence on GitHub issues, no invented numbers, real file paths only; the reviewer must cite a file and line or a
  failing command for a FAIL (L4, L9).
- The lead works the backlog on its own (wave order, at most 2 issues in flight), escalates only IAM, cost and scope,
  and never writes product code (L15).
- The deployer records the previous revision, rolls back on failed checks, and deploys as the dedicated runtime SA
  (L7).
- The OpenCode launcher writes a pinned model catalog on every start instead of deleting it (L3).
- The eval team has an explicit data contract: Spanner, GitHub, Firestore and the bucket; unknown values are shown as
  "n/a" (L9).
- Leftovers removed: `harness: gemini` in the eval templates, `home/.hermes/config.yaml` (the launcher rewrites it on
  every start), `env: SCION_TELEMETRY_ENABLED` (overridden by the Hub, L6).

The [v2 design](../specs/factory-orchestration-v2-design.md) (one worker and one PR per issue, status labels, a
`factoryctl` helper) needs further template changes; these templates are the shared-workspace version that runs
today.
